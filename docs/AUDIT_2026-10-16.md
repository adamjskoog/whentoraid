# App audit — October 16, 2026

Production assessment: **74/100, launchable with caveats for a controlled beta.** The scheduling core has substance, but the evidence does not justify an unrestricted production sign-off. The biggest remaining uncertainty is the real online lifecycle: Discord authentication, database authorization, live synchronization, message delivery, and recovery working together against the deployed configuration. This is an engineering judgment, not a calculated quality metric.

Reviewed the working tree based on `3cd79d5`, with a clean starting state. Changes are local and uncommitted. No hosted migration, deployment, real Discord message, or production account change was performed.

## Candid product assessment

The app solves a real coordination problem and already handles more than a simple availability poll: multiple characters, role composition, publication snapshots, late responses, attendance, timezone conversion, and conflicting commitments. Pure scheduling helpers, database permission checks, and explicit recovery paths are valuable foundations.

The experience still feels designed by someone who knows every feature. Setup presents online sign-in, browser-only creation, a large guild/character form, two demo entry points, and restore options together. On phones, the user must scroll through substantial configuration before creating anything. A new player needs a clearer first decision: join an existing guild, create a shared guild, or explore a sample.

The dark visual identity is coherent. The planner's Schedule/Roster/Responses tabs help, and the tested pages fit narrow screens. However, the interface uses many small captions, panels, disclosures, and competing statuses. The schedule view repeats roster/readiness information in a tall right column and leaves considerable unused space below the main task. The next visual improvement should reduce information and decisions per screen rather than add more decoration.

Browser-only mode is useful for a demo or a single planner, but its limitations remain fundamental: there is no real identity boundary, storage belongs to one browser, and simultaneous local edits are not merged. Shared guilds should be the primary path for actual collaborative use.

## Remaining risks, in priority order

1. **Release evidence is incomplete.** The Docker daemon is unavailable, so this audit could not execute pgTAP or the local API/Edge Function integration suite. CI workflows declare these gates, but current remote CI status and hosted configuration were not verified. Before a public release, run both suites on the final revision and verify officer/player separation against a safe staging guild.
2. **The real Discord lifecycle needs a recorded acceptance run.** Browser coverage mocks Discord; it does not prove OAuth callback configuration, bot permissions, deployed secrets, cron/Vault scheduling, or real message editing. Verify publish, republish, cancel/withdraw, confirm/decline, reminder deduplication, and revoked calendar links. Earlier project notes explicitly identify real-channel testing as pending.
3. **Operational visibility is weaker than feature coverage.** There are function logs, persisted delivery outcomes, retries, and recovery controls, but no repository evidence of an end-to-end health probe or alerting for stalled reminder delivery. Add a staging probe and an operational view of queue age/failures before promising dependable automated reminders. Do not log calendar bearer tokens or webhook URLs.
4. **Setup is overloaded and repeats the demo offer.** Separate the first decision from guild/character details, make joining prominent, and defer optional configuration. Measure completion on a phone with someone unfamiliar with the app.
5. **Local collaboration is still last-write-wins.** Fixing the active player does not provide an atomic merge of two nearly simultaneous localStorage writes. Use online mode for shared editing; a future local-mode improvement could offer conflict detection instead of silently replacing a competing edit.
6. **Accessibility coverage remains partial.** The changes address observed dialog, focus, validation, and text-size defects. No full axe audit, screen-reader session, zoom/reflow review, or real iPhone/Safari pass was completed. Pixel emulation is Chromium, not an iOS compatibility test. Some secondary controls and captions are still small. Account-operation errors in `OnlineAccount.svelte` now appear inside the account panel (follow-up, below).
7. **Performance has not been measured under realistic conditions.** The baseline production JavaScript was about 516 kB uncompressed / 158 kB gzip, with a single main bundle. Google Fonts adds external requests. There are no measured field Core Web Vitals here. Profile a large online guild on a throttled phone before choosing route splitting or changing sync granularity; each realtime change currently leads to a guild snapshot reload.
8. **Deployment reproducibility can improve.** Edge Functions now import `npm:@supabase/supabase-js@2.117.2`, matching the frontend lockfile (follow-up, below); bump both together. Existing atomic-write rollback documentation is useful, but does not demonstrate recovery of every later integration/configuration change.
9. **Maintainability is becoming expensive.** `Planner.svelte` and `remote/sync.svelte.js` combine many workflows and state transitions. Extract publication/delivery coordination and channel/session lifecycle in focused follow-ups, with behavior tests. A sweeping rewrite would add risk without proving a user benefit.
10. **Backup validation is not a complete resource-budget policy.** The added checks reject the demonstrated corrupt structures, and backups over 10 MB are now refused before reading (follow-up, below). Broader fuzzing remains useful protection against unusual imported documents.

## Follow-up fixes (same day)

- Account errors (risk 6): sign-in, guild switching, demo/online creation, and sign-out failures now show as an alert inside the account panel instead of a toast. Covered in `OnlineAccount.test.js`.
- SDK pinning (risk 8): all five Edge Function entry points pin `@supabase/supabase-js@2.117.2`. Not exercised against a deployed function; takes effect on the next `supabase functions deploy`.
- Backup size (risk 10): `MAX_BACKUP_BYTES` (10 MB; the year-long demo guild is about 0.8 MB) is checked against the file size before reading and the text length before parsing. Covered in `storage.test.js`.

## Security and data review boundaries

Inspected client auth setup, invite handling, online save/recovery, local sign-in restrictions, Discord installation state validation, dispatch authorization, signed interaction entry points, calendar token handling, and representative access/atomic-write/hardening migrations and tests. The inspected code uses server permission checks, restricted privileged functions, verified Discord identity, and separate published roster state. Only `.env.example` is tracked among the root `.env*` files checked.

No new authorization bypass was established in this review. That statement is limited to inspected source and tests; it is not proof that the hosted policies, enabled auth providers, redirect allowlists, or secrets match the repository. No external dependency/CVE scan or complete Git-history secret scan was performed.

## Verification and limits

- Baseline: lint, formatting, 438 unit/component tests, and production build passed.
- Final `npm run check`: lint and formatting passed; **463 tests in 53 files passed**; production build passed. The build retains a bundle-size warning: approximately 519 kB JavaScript / 159 kB gzip for the configured backend build.
- Final `npm run test:e2e -- --workers=2`: **66 passed, 2 intentional platform-specific skips**, across desktop Chromium and Pixel 7 emulation. The first-install offline and recovery-download tests pass in both projects.
- Browser review covered setup and all six main views at 1440, 768, 375, and 320 pixels. The baseline run recorded no page JavaScript exceptions or horizontal overflow. Representative desktop planner, mobile setup, and mobile availability screenshots were inspected.
- Added behavioral coverage for malformed imports, storage failure and recovery download, active-player isolation between tabs, accessible dialog/error behavior, route titles/focus, mobile form sizing, realtime resubscription, cache isolation/failure handling, and first-install offline reload.
- Local before/after screenshots and measurements are under `test-results/audit/` and `test-results/audit-after/`; browser artifacts are under `test-results/e2e/`. The after run checked 24 view/viewport combinations with no page JavaScript exceptions or horizontal overflow. These are ignored local artifacts, not a committed visual baseline. Automated screenshot regression comparison is therefore **inconclusive**.
- Database/integration execution, hosted smoke tests, real Discord delivery, Safari/Firefox, full assistive-technology testing, and performance budgets remain unverified.

The next release gate is a staging run through sign-in → join → availability → publish → Discord response → cancellation/calendar update, including a disconnected/reconnected viewer, followed by the database and integration suites. Until that evidence exists, treat this as a capable beta with known operational gaps.
